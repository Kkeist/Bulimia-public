# 模块构建规则

模组应先写 **MODULE_STRUCTURE.md**（结构设计），再按该文档转成 `module.json`。不要先写 JSON，否则难以维护、难以保证层级与条件一致。

---

## 一、流程：先 Structure，再 JSON

1. **先写 MODULE_STRUCTURE.md**  
   - 用人类可读的层级与字段，把模块树、分流程、每个模块的 id/名/类型/条件/变量/插件/总结等写清楚。  
   - 结构图（含锚点、回链）和「各模块说明」是唯一真相来源。  

2. **再根据 Structure 生成 module.json**  
   - 按 MODULE_STRUCTURE 中的「六、凭本设计生成 module.json 说明」做字段映射、conditionDef 展开、entryEvent 与树结构还原。  
   - 生成后可用「七、测试内容类型覆盖检查」核对是否覆盖所有需测类型。  

3. **迭代时**  
   - 改设计只改 MODULE_STRUCTURE；改完再重新生成或手改 module.json，保持二者一致。  

---

## 二、Structure 文档应包含的章节

建议与模组内 MODULE_STRUCTURE.md 同构，便于转换与测试：

| 章节 | 内容 |
|------|------|
| **一、结构图** | 总模块下 Main / 各分流程；时间线、触发器链、自由触发器分组；节点带 `[名](#id)` 锚点；上下顺序即链顺序。 |
| **二、完整结构图** | 与第一节同构，在每节点下补充**变量**（id）、**插件**（id）；无则可省略。 |
| **三、模块构建规则** | 设计规则摘要 + 时间/历法等约定；可引用本 BUILD_RULES。 |
| **四、各模块说明** | 每个模块一条，字段见 [bulimia 数据结构](../docs/bulimia数据结构.md)：模块id、模块名、流程、类型、变量、插件、进入条件、完成条件、模块info、投递info、标签、队列展示、linkedList、总结等；无则写「无」。 |
| **五、各分流程说明** | 每个分流程（非 main）单独一段：分流程 id、**entryEvent**、进入条件、总结。 |
| **六、凭本设计生成 module.json 说明** | 字段映射、conditionDef 展开规则、entryEvent 取值、树结构还原、变量与插件转换。 |
| **七、测试内容类型覆盖检查** | 对照 05-test-module / 01-core-schemas，表格式列出是否包含各需测类型（模块类型、时间/条件、变量、插件、flow、总结、queueDisplay 等）。 |

每个模块说明末尾加 `[↑ 回结构图](#structure-map)`，便于从正文跳回结构图。

### 3.3 各模块说明（单条模板）

每个模块一条，标题用 `### 模块名`，锚点用 `<a id="模块id"></a>`（与结构图中的 `#模块id` 一致）。字段见 [bulimia 数据结构](../docs/bulimia数据结构.md)，无则写「无」。

**字段约定**：模块id、模块名、流程、类型、变量、插件、模块备注、进入条件、完成条件、模块info、投递info、标签、队列展示、linkedList、总结（可选）。  
**condition**：一律 `precondition` 或 `display`，conditionDef 用 ① ② … 列出，多条件写明 **logic**: AND 或 OR。

**单条复制模板**（替换占位后逐模块使用）：

```
<a id="模块id"></a>
### 模块名

- **模块id**: `模块id`
- **模块名**: 模块名
- **流程**: `main` | `分流程id`
- **类型**: 时间线 | 触发器链 | 自由触发器
- **变量**
  - 变量id: `变量id`
    - 变量名称: 变量名称
    - 变量type: string | number | boolean | list_of_object | …
    - 变量类型: 模块变量 | 开关变量 | 内置变量
    - 初始值: …
    - 变量更改规则: …
  （无则写「**变量**：无。」）
- **插件**
  - 插件id: `插件id`
    - 插件名称: 插件名称
    - 插件备注: …（含暂存变量则写明 id、名称、type）

  （无则写「**插件**：无。」）
- **模块备注**: 仅调试用，不发给 AI。
- **进入条件**
  - `type`: `precondition`（或 display）
  - `conditionDef`：① `type`: `module`|`variable`|`time`|…，…；② …；**logic**: AND/OR。（无则写「无」。）
- **完成条件**
  - 无。（或有则同进入条件格式。）
- **模块info**
  - ① `content`: "…"；`condition`: 无 或 具体 condition。
- **投递info**
  - 无。（或有则 ① `title`: "…", `content`: "…", `condition`: …；completed 由系统默认，不写。）
- **标签**：无。（或有则 `["tag1", "tag2"]`。）
- **队列展示**：无。（或仅事件模块写 before/after 两数字。）
- **linkedList**：仅触发器链；`{ "prev": "上节点id或null", "next": "下节点id或null" }`。

```

## 四、写 Structure 时的设计规则

### 4.1 触发器链是中心

- 每个模块（含总模块）下，**主线以触发器链为核心**：玩家从链上第一个节点进入，按顺序推进；时间线和自由触发器在满足条件时与链**并行**触发，不替代链。  
- 若某模块旗下**没有**触发器链，该模块内当前事件会处于 **floating** 状态。因此：**每个模块旗下应尽量包含触发器链**，除非该模块是“纯自由探索”而无主线。

### 4.2 最外层放什么

- **最外层触发器链**：表示**阶段/时代**（例：凡人 → 炼气 → 筑基），每个阶段节点内再细分时间线/链/自由。  
- **最外层时间线**：只放**不限于某一阶段**的全局事件。  
- **阶段内时间线**必须放在**对应阶段或分流程模块内**的时间线里，不要放在最外层再加“境界条件”。  
- 任意父级对子级同理：谁属于谁，用层级表达，不用“同层 + 一堆条件”代替。

### 4.3 层级与包含关系

- **父子关系要清楚且有效**：子模块写在父模块旗下，就表示在父模块范围内发生。  
- 同一层级内：先时间线、再触发器链、再自由触发器（顺序可依习惯，但类型分组清晰）。  
- 树保持平衡：同一层兄弟不宜过多，层级用足，便于阅读和后续扩展。

### 4.4 条件与字段约定

- 所有 **condition** 必须为 `precondition` 或 `display`，**conditionDef** 为可落代码的结构（`type`、`variableId`、`moduleId`、`state`、`time`、`timeType`、`operator`、`value` 等），禁止纯人类语言描述。  
- **默认条件不写入**：① 必须进入父级才能进入子级（树保证）；② 触发器链：链上前一节点（linkedList.prev）已完成；③ 分流程：entryEvent 对应模块已完成。以上由**系统**在判定时自动加入，模组内**不写**进 entryConditions，只写变量、时间等除此以外的条件。  
- 进入条件/完成条件：多条时写明 **logic**: AND 或 OR；单条或无则写「无」。  
- 时间线模块的进入条件必须包含**时间相关**条件（`time` 或 `time_range`）；触发器链必须写 **linkedList**（prev/next）。  
- 变量只列模块变量、开关变量、内置变量；**暂存变量归插件所有**，写在插件备注中，不列在模块变量下。  
- 分流程必须在「各分流程说明」中**显式写出 entryEvent**（module-id 或 null），生成 module.json 时直接使用。

### 4.5 系统默认与禁止在模组中写入

以下由**系统**约定，**禁止在具体模组 MODULE_STRUCTURE 或 module.json 里写任何一条，也禁止在模组内写解释性括号**。解释只放在本规则与 01-core-schemas 等指导里。

| 项目 | 系统行为 | 模组中 |
|------|----------|--------|
| **进入条件为空** | 无任何前置时，不写 conditionDef；不写 `type: none` 等占位。 | 只写「无」。 |
| **父级/链前序/entryEvent** | 系统自动加：① 必须进入父级才能进入子级 ② 链上前一节点已完成 ③ 分流程 entryEvent 已完成。 | 不写入 entryConditions，不写「由系统默认」等解释。 |
| **info / deliveryInfo 的 completed** | 未投递完成前默认为 false。 | 不写 `completed: false`。 |
| **队列展示 queueDisplay** | before/after 表示当前事件时队列显示条数，语义由系统实现。 | 只写数值，如 `before`: 2，`after`: 2；不写「处于本事件时…」等解释。 |
| **总结 promptList 的 condition** | condition 无时表示按子模块完成等系统约定触发总结。 | 只写「无」或具体 condition；不写「子模块完成时各总结一次」等解释。 |
| **entryEvent** | 分流程入口由系统强制校验。 | 只写 `entryEvent`: `模块id` 或 null；不写「由系统强制」「不必再写」等解释。 |

## 五、从 Structure 到 JSON 的要点

- **字段名**：按 Structure 的「六」做映射（如 模块id → id，类型 时间线 → timeline）。  
- **conditionDef**：设计中的 ① ② … logic 需展开为 01-core-schemas 的 `{ logic, groups: [ { logic, items: [ { itemType: "condition", condition: { ... } } ] } ] }`。  
- **树与 flow**：由结构图唯一确定；每个 flow 的 subModules 顺序与结构图一致；递归子模块同样按图展开。  
- **entryEvent**：从各分流程说明中读取，不推断。
